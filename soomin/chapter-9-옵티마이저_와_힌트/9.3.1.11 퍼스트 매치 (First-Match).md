# 0. 학습 목적
- 퍼스트 매치의 세미 조인 최적화 원리를 이해한다.
- `IN-to-EXISTS` 최적화와 비교했을 떄 가지는 장점을 이해한다. 

# 1. 퍼스트 매치 (FIrst-Match)란? 
외부 테이블 레코드와 조인 조건 상 일치하는 최초의 내부 테이블 레코드를 발견하면 그 이후 탐색을 그만두는 최적화 기법이다. IN 대신 `Exist` 쿼리를 썼을 때 나는 효과와 똑같다. 

## (1) 예시
![erd.png](https://raw.githubusercontent.com/dalcheonroadhead/img-cloud/main/2025-07/20250806002040.png)

```sql
SELECT *
FROM employees e
WHERE e.emp_no < 3
AND e.emp_no IN (
	SELECT t.emp_no
	FROM titles t
	WHERE t.from_date BETWEEN '2025-07-01' AND '2025-07-30'
)
```

![image.png](https://raw.githubusercontent.com/dalcheonroadhead/img-cloud/main/2025-07/20250806004744.png)

# 2. 실행 계획상 표시
```sql
id    table    type      key            rows     Extra
1     e        ref      ix_first_name   233      NULL
1     t        ref      PRIMARY         1        Using Where; Using Index; FirstMatch(e)
```
퍼스트 매치가 실행되었다면 Extra 부분에 `First Match (First Match를 주도한 테이블의 이름/별칭)`
으로 작성된다.

# 3. 특징
1. 퍼스트 매치는 옵티마이저가 서브쿼리에 활용할지 취사 선택할 수 있다. (`IN-to-EXISTS` 방법과의 차이점) 
2. 퍼스트 매치는 `상관 서브쿼리`여도 활용할 수 있다.
3. 퍼스트 매치는 서브 쿼리 내에 `GROUP BY` 나 `집합 함수`가 존재하면 활용할 수 없다.

## (1) `IN-to-EXISTS` 최적화 전략과의 차이점
`IN-to-EXISTS` 최적화 전략은 말 그대로 IN을 EXISTS로 바꾸어 쿼리 튜닝하겠다는 것이다. 만약 서브쿼리 체인이 2개 이상일 경우, 최외곽 서브쿼리를 IN에서 EXISTS로 바꾼다면 어쩔 수 없이 모든 서브쿼리가 `FIRST MATCH` 방식으로 진행된다.

하지만 `IN`은 그대로 놔두고 옵티마이저 옵션의 `firstmatch`를 사용하면 특정 서브쿼리에만 firstmatch가 적용되도록 취사선택이 가능하다. 즉 옵티마이저에게 자유를 준다.
### 취사 선택 해야하는 경우는 언제일까? 
서브쿼리로 생긴 임시 테이블 결과를 쿼리 도중에 재활용해야 하는 경우이다. (즉 세미 조인이 아닌 서브쿼리가 서브 쿼리 체인에 끼여 있을 경우이다.)



# 4. 핵심 요약
1. `firstmatch` 옵션은 `IN-to-EXISTS` 전략을 옵티마이저 옵션으로서 나타낸 것이다.
2. 수동적인 `IN-to-EXISTS` 최적화 전략과 비교했을 때 `firstmatch` 옵션은 옵티마이저에게 exists 방식을 쿼리 전반에 적용할지 몇 개의 서브 쿼리에만 적용할지 취사 선택할 수 있게 해주는 자유를 준다는 장점이 있다.
